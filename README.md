# Social Media API --- FastAPI + PostgreSQL

A REST API for a social media application built with **FastAPI**,
**SQLAlchemy**, and **PostgreSQL**. It supports user registration and
login, role-based administration, posts, likes, comments, comment
pinning, and comment permissions.

> **Schema note:** This README documents the database design and
> implementation described during development. The PostgreSQL database
> was created separately with SQL. The application should map to the
> existing tables; do not run `Base.metadata.create_all()` against this
> database unless you intentionally want SQLAlchemy to create tables.

## Technology Stack

## Configuration and Security

The `.env` file should contain the database connection and JWT
configuration. Example keys:

``` dotenv
DATABASE_URL=postgresql+psycopg://USER:PASSWORD@HOST:5432/social_media_db
SECRET_KEY=replace_with_a_long_random_secret
ALGORITHM=HS256
ACCESS_TOKEN_EXPIRE_MINUTES=30
```

Use real values only in your local `.env` file. **Never commit `.env`,
passwords, database credentials, or JWT tokens to Git.** Add `.env` to
`.gitignore`.

Passwords are stored as password hashes, not plain text. Protected
endpoints expect a bearer token in the `Authorization` header:

``` http
Authorization: Bearer <access_token>
```

## Database Tables

The application uses four core tables: `users`, `posts`, `comments`, and
`likes`.

### 1. `users`

Stores account details, authentication data, role, and account status.

  -----------------------------------------------------------------------
  Column                              Purpose
  ----------------------------------- -----------------------------------
  `id`                                UUID primary key; generated by
                                      PostgreSQL using
                                      `gen_random_uuid()`

  `username`                          Required username; unique; maximum
                                      length documented in the model as
                                      50

  `email`                             Required email address; unique

  `password_hash`                     Required password hash; never store
                                      the original password

  `role`                              Role value, normally `user` or
                                      `admin`; defaults to `user`

  `created_at`                        Account creation timestamp;
                                      defaults to `CURRENT_TIMESTAMP`

  `is_blocked`                        Boolean account status; defaults to
                                      `false`
  -----------------------------------------------------------------------

**Constraints and relationships**

-   Primary key: `id`
-   Unique values: `username`, `email`
-   Role check constraint restricts values to `user` and `admin`
-   `users.id` is referenced by `posts.user_id`, `comments.user_id`, and
    `likes.user_id`
-   Deleting a user cascades to related posts, comments, and likes where
    foreign keys use `ON DELETE CASCADE`

### 2. `posts`

Stores posts created by users and the setting controlling whether
comments are permitted.

  -----------------------------------------------------------------------
  Column                              Purpose
  ----------------------------------- -----------------------------------
  `id`                                UUID primary key; generated by
                                      PostgreSQL using
                                      `gen_random_uuid()`

  `user_id`                           Foreign key to `users.id`;
                                      identifies the post owner

  `title`                             Required post title

  `content`                           Required post body

  `comments_allowed`                  Boolean; defaults to `true`;
                                      controls whether new comments may
                                      be created

  `created_at`                        Creation timestamp; defaults to
                                      `CURRENT_TIMESTAMP`

  `updated_at`                        Update timestamp if present in the
                                      actual table/model
  -----------------------------------------------------------------------

**Constraints and relationships**

-   Primary key: `id`
-   `user_id` references `users.id` with `ON DELETE CASCADE`
-   A user can own many posts
-   Posts are ordered newest first by `created_at DESC`, with `id DESC`
    as a tie-breaker in public listing
-   The `comments_allowed` value is changed by the post owner or an
    admin

> Confirm the exact `title` length and whether `updated_at` exists using
> `\d posts` in `psql` or the table properties in pgAdmin. The model and
> database schema should agree.

### 3. `comments`

Stores comments that users write on posts.

  -----------------------------------------------------------------------
  Column                              Purpose
  ----------------------------------- -----------------------------------
  `id`                                UUID primary key; generated by
                                      PostgreSQL using
                                      `gen_random_uuid()`

  `post_id`                           Foreign key to `posts.id`

  `user_id`                           Foreign key to `users.id`;
                                      identifies the comment author

  `content`                           Comment text

  `created_at`                        Creation timestamp; defaults to
                                      `CURRENT_TIMESTAMP`

  `updated_at`                        Last-update timestamp

  `is_pinned`                         Boolean; defaults to `false`;
                                      indicates whether the comment is
                                      pinned
  -----------------------------------------------------------------------

**Constraints and relationships**

-   Primary key: `id`
-   `post_id` references `posts.id` with `ON DELETE CASCADE`
-   `user_id` references `users.id` with `ON DELETE CASCADE`
-   The post owner can pin or unpin comments on their post
-   A partial unique index named `idx_one_pinned_comment_per_post` on
    `post_id` where `is_pinned = true` enforces at most one pinned
    comment per post
-   The index `idx_comments_post_created` on
    `(post_id, created_at DESC)` supports retrieving a post's comments
    in creation-time order
-   Comment creation is rejected when the related post has
    `comments_allowed = false`
-   Comment editing and deletion are restricted to the comment author in
    the implemented endpoints

### 4. `likes`

Stores the relationship between a user and a post they have liked.

  -----------------------------------------------------------------------
  Column                              Purpose
  ----------------------------------- -----------------------------------
  `user_id`                           Foreign key to `users.id`

  `post_id`                           Foreign key to `posts.id`

  `created_at`                        Timestamp for the like; defaults to
                                      `CURRENT_TIMESTAMP`
  -----------------------------------------------------------------------

**Constraints and relationships**

-   Composite primary key: `(user_id, post_id)`
-   `user_id` references `users.id` with `ON DELETE CASCADE`
-   `post_id` references `posts.id` with `ON DELETE CASCADE`
-   The composite primary key prevents the same user from liking the
    same post more than once
-   A user can like many posts, and a post can receive likes from many
    users

### Entity Relationship Overview

``` text
users
  | 1
  |------< posts.user_id
  |          |
  |          | 1
  |          |------< comments.post_id
  |          |
  |          |------< likes.post_id
  |
  |------< comments.user_id
  |
  |------< likes.user_id
```

-   One user can create many posts.
-   One post can have many comments and many likes.
-   One user can create many comments and likes.
-   A like is unique for each `(user_id, post_id)` pair.

## API Implementation Phases

The phases below follow the project's development plan. Phase 7 was
initially skipped and then implemented later.

### Phase 1 --- Project and Database Connection

-   Configure FastAPI and Uvicorn.
-   Load database settings from `.env`.
-   Create the SQLAlchemy engine and session factory.
-   Use `get_db()` as a dependency to provide and close database
    sessions.
-   Check connectivity by querying `SELECT current_database()`.

Relevant file: `app/database.py`

### Phase 2 --- SQLAlchemy Models and Pydantic Schemas

-   Map Python model classes to the existing PostgreSQL tables.
-   Use Pydantic models to validate incoming request bodies and define
    response shapes.
-   Keep ORM models separate from API request/response schemas.
-   The database schema is maintained with SQL; avoid accidental schema
    recreation.

Relevant files: `app/models.py`, `app/schemas.py`

### Phase 3 --- User Registration

-   Endpoint: `POST /auth/register` (confirm the exact path in Swagger).
-   Accept username, email, and password.
-   Validate input with Pydantic.
-   Hash the password before saving it.
-   Return safe user fields; never return the password hash to clients.
-   Enforce unique username and email constraints.

Relevant files: `app/auth.py`, `app/security.py`, `app/schemas.py`

### Phase 4 --- User Login and JWT Authentication

-   Authenticate using email and password.
-   Verify the submitted password against the stored password hash.
-   Issue a signed JWT access token.
-   Protected endpoints use `get_current_user` to validate the bearer
    token and load the user from PostgreSQL.
-   Blocked accounts are denied access.
-   The token expiration is configured by `ACCESS_TOKEN_EXPIRE_MINUTES`.

Relevant files: `app/auth.py`, `app/security.py`

### Phase 5 --- Roles and Admin User Management

-   Roles: `user` and `admin`.
-   `get_admin_user` ensures an authenticated user has the admin role.
-   Admin endpoints list users, block/unblock users, and delete users.
-   Regular users cannot use admin-only endpoints.
-   Deleting users can cascade to related records according to database
    foreign keys.

Relevant file: `app/admin.py`

### Phase 6 --- Post CRUD and User-Specific Posts

-   Logged-in users can create posts.
-   Users can retrieve their own posts.
-   Users can update or delete their own posts.
-   Ownership is checked against the authenticated user's ID.
-   Post deletion cascades to related comments and likes according to
    foreign-key constraints.

Relevant files: `app/posts.py`, `app/models.py`, `app/schemas.py`

### Phase 7 --- Public Posts Listing with Pagination

**Endpoint:** `GET /posts/`

-   Public: does not require a JWT.
-   Returns posts from all users, newest first.
-   Query parameters:
    -   `page`: page number, default `1`
    -   `limit`: number of posts per page, default `10`, maximum `100`
-   Invalid page or limit values return HTTP `400`.
-   An empty list is valid if there are no posts or the requested page
    is beyond the available results.

Example:

``` http
GET /posts/?page=1&limit=5
```

Offset calculation:

``` python
offset = (page - 1) * limit
```

The query uses SQLAlchemy `.offset(offset)` and `.limit(limit)` so
PostgreSQL returns only the requested subset.

### Phase 8 --- Like and Unlike Posts

-   Like endpoint: `POST /posts/{post_id}/like`
-   Unlike endpoint: `DELETE /posts/{post_id}/like`
-   Requires an authenticated user.
-   The API checks that the post exists.
-   The composite primary key `(user_id, post_id)` prevents duplicate
    likes.
-   Unlike removes the current user's like for the specified post.
-   Exact success/error messages should be checked in the current
    `app/posts.py` implementation and Swagger.

Relevant files: `app/posts.py`, `app/models.py`

### Phase 9 --- Create, Edit, and Delete Comments

-   Create comment: `POST /posts/{post_id}/comments`
-   Edit comment: `PUT /comments/{comment_id}`
-   Delete comment: `DELETE /comments/{comment_id}`
-   Requires authentication.
-   A comment is linked to its post and author.
-   Users can edit or delete their own comments.
-   Creating a comment is blocked if `comments_allowed` is `false`.
-   Request validation uses `CommentCreate` and `CommentUpdate`;
    responses use `CommentResponse`.

Relevant files: `app/comments.py`, `app/models.py`, `app/schemas.py`

### Phase 10 --- Public Comments Listing with Pagination

**Endpoint:** `GET /posts/{post_id}/comments`

-   Public: no JWT required.
-   Checks that the post exists.
-   Query parameters: `page` (default `1`) and `limit` (default `10`,
    maximum `100`).
-   Returns comments for the requested post, newest first.
-   Invalid pagination parameters return HTTP `400`.
-   A nonexistent post returns HTTP `404`.
-   Uses offset pagination: `skip = (page - 1) * limit`.

Example:

``` http
GET /posts/POST_UUID/comments?page=1&limit=10
```

### Phase 11 --- Pin and Unpin Comments

-   Pin: `PATCH /posts/{post_id}/comments/{comment_id}/pin`
-   Unpin: `PATCH /posts/{post_id}/comments/{comment_id}/unpin`
-   Requires authentication.
-   Only the post owner can pin or unpin comments on their post.
-   The endpoint verifies the comment belongs to the specified post.
-   When a different comment is pinned, the previously pinned comment is
    unpinned.
-   The database partial unique index ensures at most one pinned comment
    per post.

Relevant file: `app/comments.py`

### Phase 12 --- Allow or Disallow Comments

**Endpoint:** `PATCH /posts/{post_id}/comments-permission`

Example request to disable comments:

``` json
{
  "comments_allowed": false
}
```

Example request to enable comments:

``` json
{
  "comments_allowed": true
}
```

-   Requires authentication.
-   Only the post owner or an admin can change this setting.
-   The value is saved in `posts.comments_allowed`.
-   When comments are disabled, the create-comment endpoint returns HTTP
    `403`.
-   Existing comments are not deleted when comments are disabled.

Relevant files: `app/posts.py`, `app/schemas.py`, `app/comments.py`

## Pagination Concepts

Pagination splits a large result set into smaller pages.

-   `page` selects the page to return.
-   `limit` sets the maximum records per page.
-   `offset = (page - 1) * limit` calculates the number of records to
    skip.
-   `.offset(offset)` skips records in the SQL query.
-   `.limit(limit)` restricts the number returned.
-   `.order_by(...)` gives results a defined order.

Example for 25 records and a limit of 10:

    Page   Offset Result
  ------ -------- ----------------
       1        0 Records 1--10
       2       10 Records 11--20
       3       20 Records 21--25
       4       30 Empty list

Offset pagination is easy to implement, but new records inserted between
page requests can cause results to shift. Cursor pagination may be
preferable for very large, frequently changing feeds.

## Authorization Rules

-   Public routes do not depend on `get_current_user`.
-   Authenticated routes use `get_current_user`.
-   Admin-only routes use `get_admin_user` or an equivalent role check.
-   Users should only edit/delete their own posts and comments.
-   Only the post owner can pin or unpin comments.
-   Only the post owner or an admin can change the comments permission.
-   Blocked users should be rejected by the authentication dependency.
-   Password hashes and JWT secrets must never be included in API
    responses or committed to source control.

## Troubleshooting

### `relation already exists`

The table already exists. Inspect it instead of repeatedly running
`CREATE TABLE`:

``` sql
\d users
\d posts
\d comments
\d likes
```

### `column does not exist`

Check the actual column names and spelling with `\d table_name`. Ensure
the SQLAlchemy model matches the existing PostgreSQL schema.

### `401 Unauthorized`

Check that you logged in, copied the access token correctly, and clicked
**Authorize** in Swagger.

### `403 Forbidden`

The user is authenticated but does not have permission for that
operation, or the account is blocked.

### `404 Not Found`

Check that the post or comment UUID exists and, for comment routes, that
the comment belongs to the specified post.

### Changes do not appear in PostgreSQL

Confirm the endpoint returned a success response, that `db.commit()`
ran, and that your SQL client is connected to the same database named in
`DATABASE_URL`.
